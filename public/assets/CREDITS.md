# Asset credits

Every file under this directory is registered in the machine-readable registry at
`public/assets/asset-licenses.json`, and `npm run test:licenses`
(`scripts/check-cc0-assets.mjs`) fails if this page and the registry disagree in either
direction. This page is the human-readable view of that registry; where the two differ,
the registry is the record and the gate is the judge.

The registry is not a formality. The checker recomputes every SHA-256 from the bytes on
disk, discovers every file in this directory itself, and fails on anything it cannot
account for. Adding media without a registry entry is a red build, not a silent addition
to the release artifact.

## Classification summary

| Class | Entries | May enter the default PixiJS bundle |
| --- | --- | --- |
| `cc0-approved` | 0 | Yes |
| `procedural` | 7 | Yes |
| `repository-authored` (non-media) | 2 | No — not media, and MIT is not CC0 |
| `legacy-unverified` | 90 | **No** |

**No asset in this directory is currently classified `cc0-approved`, because none of them
has a verified CC0 grant.** That is the honest state of the repository, not a gap in the
search: the CC0 media policy in plan section 10.3 and ADR 002 Decision 5 says only CC0 or
procedurally generated media may enter the default PixiJS bundle, and nothing in the sprite
set can currently claim CC0. Phase 10 declared the five further bundle sets and, as its
non-goals require, produced no world-specific media for them — so the number is still 0
after Phase 10, and it will only rise when a genuinely CC0 file is registered here.

## The four classes

- **`cc0-approved`** — media verified as CC0 1.0 with a creator or source, a source URL
  where applicable, the exact `CC0-1.0` identifier, the license URL, a retrieval or
  creation date, a SHA-256 checksum, and a modification record. Admitted to the default
  PixiJS bundle.
- **`procedural`** — generated by a committed script, so no third-party license attaches.
  The recipe is recorded, the generating script has to exist, and the digest is recomputed
  from the file. Admitted to the default PixiJS bundle.
- **`repository-authored`** — a non-media file written in this repository rather than
  imported. It is recorded as a fourth class because the three classes above are a media
  taxonomy, and the honest description of this repository's own files is neither CC0 nor
  procedural nor unverified: they are MIT, per the repository `LICENSE`.
- **`legacy-unverified`** — pre-existing media whose license cannot be verified. These
  stay available to the legacy renderer for the length of the migration and are removed
  with Phaser; they are excluded from the default PixiJS bundle, and the gate fails if one
  is ever registered as a bundle member or placed under a bundle path.

## Legacy unverified: what is not verified, and why

All 90 entries below carry the literal license value `UNVERIFIED`, state
`licenseVerified: false`, and record the reason. None of them carries a license URL, because
none of them has a license to point at. The reason is the same in each case and it is worth
stating plainly:

- 10 of them were copied in from the [repo-dungeon](https://github.com/McFuzzySquirrel/repo-dungeon)
  project. That project's credits page describes its assets as "original lightweight
  placeholders" and records no CC0 identifier, no creator, no per-file source URL, and no
  checksum. That is an unverified license, so these are unverified.
- The other 80 were first committed by an in-repository feature commit rather than
  by the import commit, so no upstream import is claimed for them. They are still not
  approved: this repository is MIT-licensed, and MIT is not CC0-1.0, so there is no verified
  CC0 provenance to record. Their registry entries name the commit that introduced them, so
  the decision to relicense or replace any of them is a short one to make.

Marking any of these `cc0-approved` without a real grant would be a false license claim in a
file that ships, so the registry records what is known and the gate holds that line.

## Procedural media

Generated by a committed script, so no third-party license attaches. Each is reproducible:
`node scripts/generate-cozy-placeholders.mjs` rewrites the set byte for byte, and the
registry records the recipe and the seed that produced each file. They are placeholder art
for Pixi development, not final art, and they contain no SMIL and no CSS animation, so they
are inert under `prefers-reduced-motion`.

## PixiJS asset bundle sets

The registry declares six PixiJS asset bundles, and the application declares the same six
bundle ids in `src/renderers/pixi/assets/assetManifest.ts`. The gate fails if the two
disagree in either direction, so a bundle cannot be added to one file and forgotten in
the other.

| Bundle | Members today | Reserved path on disk |
| --- | --- | --- |
| `pixi-default` | 6 procedural placeholders | exists — the Cozy placeholder set above |
| `common` | 0 | not created yet |
| `village` | 0 | not created yet |
| `dungeon` | 0 | not created yet |
| `fishing` | 0 | not created yet |
| `share-card` | 0 | not created yet |

The five empty sets are declared on purpose. Phase 10 defines the bundles, their keys,
and their procedural fallback recipes, and its non-goals exclude final world-specific
asset production; with no verified CC0 grant anywhere in the repository, there is
nothing to admit. A bundle with no media is not a gap in the search — it is the honest
state, and the corresponding entries in the manifest carry keys rather than filenames.

Each empty bundle still reserves a path under this directory. That is a policy
declaration, not a provenance claim: it says where the bundle's media may live, so the
gate's tripwire is armed *before* the first file lands. Drop an unverified file under a
reserved path and `npm run test:licenses` fails with `E-UNVERIFIED-IN-BUNDLE`; drop an
unregistered file anywhere under this directory and it fails with
`E-UNREGISTERED-MEDIA`. The reserved directories are deliberately *not* under the
`sprites/` tree, where the 90 unverified legacy files live, and they are not a
place to relicense anything: MIT is not CC0-1.0, and re-licensing the legacy set is a
copyright-holder decision, not a build step.

## Adding an asset to this directory

1. Add the file under `public/assets/`.
2. Add an entry to the registry. For media, record the id, path, creator or source, source
   URL (or an explicit reason it does not apply), the exact `CC0-1.0` identifier, the license
   URL, the creation or retrieval date, a modification record, and a `generation` block if
   the file is procedural. For anything you cannot verify, classify it `legacy-unverified`
   and record why. Do not guess.
3. Run `npm run test:licenses -- --write` to record the SHA-256, then run it again to gate.
4. Add the path to this page.

Step 2 is the one that matters. An unverified asset recorded as approved is worse than a
missing feature, because it is a false claim that ships.

## Prior art

The legacy set was intended as temporary stand-ins from the start. See
[`docs/CUSTOMIZATION.md`](../../docs/CUSTOMIZATION.md) for how to swap these for your own
art, and note that anything you swap in is subject to the same registry rule: CC0 or
procedural, with a recorded provenance, or it stays out of the default PixiJS bundle.

Approved (CC0) entries: **0**. That number is the one to watch, and it is expected to
rise in a later phase that can point at a real grant — not in Phase 10, which declared
the bundle sets without producing media.
